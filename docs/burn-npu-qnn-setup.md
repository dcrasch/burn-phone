# Setting up burn-npu with the Qualcomm QNN SDK

This guide covers the Qualcomm side of this repository: building
[`burn-npu`](https://github.com/frane/burn-npu) with its QNN backend, packaging
the Hexagon runtime libraries into an Android APK, and running SqueezeNet
ops on the HTP (Hexagon Tensor Processor).

Everything here was brought up with QNN SDK **2.52.0.261104** (QNN API 2.52)
on a Linux host and verified on a Nothing Phone (Pong, Qualcomm SM8475, Android
16). Conv2d, pooling, ReLU, concat, and softmax run on the Hexagon NPU on that
device. The x86_64 emulator uses burn-npu's CPU fallback, because no Hexagon
hardware or x86_64 QNN runtime is available there.

---

## 1. How the pieces fit together

```text
Rust app (Burn Tensor)
        │
        ▼
burn-npu NpuBurnBackend
        │  conv2d, pool, relu, concat, softmax (size thresholds)
        ▼
QNN bindings (generated by bindgen at build time from the SDK headers)
        │
        ▼
libloading::Library::new("libQnnHtp.so")
        │
        ├── libQnnHtpV<N>Stub.so   (CPU-side HTP stub, dlopen'd by libQnnHtp)
        └── libQnnHtpV<N>Skel.so   (DSP-side skeleton, loaded via ADSP_LIBRARY_PATH)
```

- `burn-npu` is a Burn backend. Ops without an NPU route run through
  `burn-flex` on the CPU.
- The NPU ops in section 7.1 attempt QNN first. Any failure returns to the CPU
  path, so the backend never produces a wrong result just because the NPU is
  unavailable.
- QNN bindings are generated at build time from `$QNN_SDK_ROOT/include/QNN`.
  Without the SDK the crate still builds and runs on CPU; it simply does not
  contain the QNN code path.

## 2. Version compatibility

| Component | Version |
| --- | --- |
| Rust | 1.92+ (Burn 0.21 minimum) |
| Burn | 0.21 |
| burn-npu | 0.4.0 |
| QNN / QAIRT SDK | 2.52.0.261104 |
| QNN API | 2.52 |
| Android minSdk | 28 |

### 2.1 Why this repository vendors burn-npu

Upstream burn-npu 0.4.0 was written against QNN API 2.31 and contains several
assumptions that do not match SDK 2.52:

1. It reads the interface function table as
   `(*provider).__bindgen_anon_1.v2_31`. SDK 2.52 generates `v2_52`.
2. It uses the type `QNN_INTERFACE_VER_TYPE`, which is a C preprocessor macro,
   not a bindgen type. Bindgen emits
   `QnnInterface_ImplementationV2_29_t` instead.
3. `Qnn_TensorV1_t::clientBuf` lives inside an anonymous union, so bindgen
   exposes it as `__bindgen_anon_1.clientBuf`.
4. `detect()` has no Android branch, so `NpuVendor::Qualcomm` is never reported
   on a phone.
5. It does not report whether a matmul actually reached the NPU or silently
   fell back to CPU.

The local copy in `vendor/burn-npu` fixes all five while staying compatible
with future QNN versions:

- `build.rs` parses `QNN_API_VERSION_MAJOR/MINOR` from `QnnCommon.h` and emits
  the correct `QNN_INTERFACE_VER_TYPE` alias after bindgen runs.
- `qnn.rs` reads the interface union through a pointer instead of a
  version-specific field name.
- `qnn.rs` uses the generated anonymous union field for `clientBuf`.
- `qnn.rs` also looks for `libQnnHtp.so` next to the paths in
  `ADSP_LIBRARY_PATH`, which helps on Android.
- `detect.rs` reads `ro.soc.model`, `ro.board.platform`, and `ro.hardware` via
  `getprop` on Android.
- `backends::qualcomm` exposes `npu_dispatch_count()` and `qnn_compiled()` so
  the UI can distinguish an NPU dispatch from a CPU fallback.
- `qnn.rs` sets `version = QNN_TENSOR_VERSION_1` on each tensor and
  `QNN_OPCONFIG_VERSION_1` on the MatMul op. Without these, QNN reads a zeroed
  union and the process segfaults inside `libQnnHtp.so`.
- `qnn.rs` marks each tensor's quantization definition as
  `QNN_DEFINITION_DEFINED` with `QNN_QUANTIZATION_ENCODING_UNDEFINED`. Otherwise
  QNN rejects the MatMul with `Use of QNN_DEFINITION_IMPL_GENERATED tensor not
  supported as input`.
- `qnn.rs` stores the tensor IDs QNN assigns during graph construction in the
  graph cache and sets them again on every execute. Otherwise execution fails
  with `Expected Tensor ID: 1 not found in user-provided tensors`.
- `build.rs` passes the NDK sysroot and target triple to bindgen when
  cross-compiling for Android (see section 4.1).

If you replace the vendored crate with a newer upstream release, re-check
those points before assuming the QNN path works.

## 3. Download the QNN SDK

### 3.1 Automatic setup

The repository's `justfile` downloads and extracts the SDK:

```sh
just qnn-setup
just qnn-status
```

Defaults:

```text
QNN_VERSION = 2.52.0.261104
QNN_CACHE_DIR = ~/.cache/burn-phone
QNN_SDK_ROOT = ~/.cache/burn-phone/qairt/2.52.0.261104
```

You can override any of them:

```sh
QNN_VERSION=2.52.0.261104 \
QNN_SDK_ROOT="$HOME/qnn/2.52" \
just qnn-setup
```

The download is about **1.26 GiB**, and the extracted SDK is about **3.1 GiB**.

### 3.2 Manual download

```sh
VERSION=2.52.0.261104
URL="https://softwarecenter.qualcomm.com/api/download/software/sdks/Qualcomm_AI_Runtime_Community/All/${VERSION}/v${VERSION}.zip"

mkdir -p "$HOME/.cache/burn-phone/qairt"
curl -fL --retry 3 -o "/tmp/qnn-${VERSION}.zip" "$URL"
unzip -q "/tmp/qnn-${VERSION}.zip" -d "$HOME/.cache/burn-phone"

export QNN_SDK_ROOT="$HOME/.cache/burn-phone/qairt/${VERSION}"
```

`QNN_SDK_ROOT` is the directory that contains `include/QNN` and `lib/`:

```text
$QNN_SDK_ROOT/
├── include/QNN/QnnInterface.h
├── include/QNN/QnnTypes.h
├── lib/aarch64-android/          # Android arm64 runtime libraries
├── lib/hexagon-v68/unsigned/     # DSP skels per Hexagon generation
├── lib/hexagon-v69/unsigned/
├── lib/hexagon-v73/unsigned/
├── lib/hexagon-v75/unsigned/
├── lib/hexagon-v79/unsigned/
└── lib/hexagon-v81/unsigned/
```

To persist it:

```sh
echo "export QNN_SDK_ROOT=$HOME/.cache/burn-phone/qairt/2.52.0.261104" >> ~/.bashrc
```

### 3.3 Check the API version

```sh
grep -E "QNN_API_VERSION_(MAJOR|MINOR|PATCH)" \
  "$QNN_SDK_ROOT/include/QNN/QnnCommon.h"
```

For this repository the expected output is:

```c
#define QNN_API_VERSION_MAJOR 2
#define QNN_API_VERSION_MINOR 29
#define QNN_API_VERSION_PATCH 0
```

## 4. Build-time requirements

QNN bindings are generated with `bindgen`, which needs `libclang`:

```sh
sudo apt install clang libclang-dev
clang --version
ldconfig -p | grep libclang
```

`burn-npu`'s `build.rs` uses `QNN_SDK_ROOT` and warns if it is unset or
invalid:

```text
warning: QNN_SDK_ROOT not set; the qualcomm feature will run on CPU.
```

### 4.1 Android (cross) builds

When cross-compiling for `aarch64-linux-android`, bindgen runs clang on the
host. Without extra arguments clang picks up the host's glibc headers instead
of the NDK sysroot and fails with:

```text
bindgen failed on the QNN headers: clang diagnosed error:
/usr/include/gnu/stubs.h:7:11: fatal error: 'gnu/stubs-32.h' file not found
```

The build then succeeds, but without `cfg(qnn_sdk)`, so the app reports
`QNN SDK: bindgen did not run` on the phone. The `build.rs` in the `burn-npu`
dependency avoids this by adding these clang arguments whenever `TARGET`
contains `android`:

```text
--target=aarch64-linux-android28
--sysroot=$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/linux-x86_64/sysroot
-I<sysroot>/usr/include/aarch64-linux-android
```

`ANDROID_NDK_HOME` must point at the NDK, as set in the Android guide. Check
the result in the build output:

```sh
grep qnn_sdk target/aarch64-linux-android/debug/build/burn-npu-*/output
# cargo:rustc-cfg=qnn_sdk
```

When the SDK is found, `build.rs`:

1. writes a small wrapper header including `QnnInterface.h`, `QnnTypes.h`, and
   friends,
2. runs bindgen with `-I$QNN_SDK_ROOT/include/QNN`,
3. appends a `QNN_INTERFACE_VER_TYPE` alias for the SDK's versioned interface
   struct,
4. emits `cargo:rustc-cfg=qnn_sdk`, which enables the runtime module.

The SDK is a **build-time input only**. Nothing is linked against at build
time; `libQnnHtp.so` is opened at runtime with `libloading`.

Add the dependencies to the app:

```toml
[dependencies]
burn = "0.21"
burn-npu = { git = "https://github.com/dcrasch/burn-npu/", branch = "support-hexagon", features = ["qualcomm"] }
libloading = "0.9"
```

Then build with the SDK visible:

```sh
export QNN_SDK_ROOT="$HOME/.cache/burn-phone/qairt/2.52.0.261104"
cargo apk build
```

If you change `QNN_SDK_ROOT`, force a rebuild of the binding crate:

```sh
cargo clean -p burn-npu -p burn-phone
```

## 5. Package the Android runtime libraries

The QNN SDK's Android libraries are in `lib/aarch64-android`, and the Hexagon
skels are in `lib/hexagon-v<N>/unsigned`.

### 5.1 What each library does

| File | Role |
| --- | --- |
| `libQnnHtp.so` | HTP backend. This is the library burn-npu opens. |
| `libQnnSystem.so` | System/context binary support. Optional for this matmul demo, but commonly packaged. |
| `libQnnHtpV<N>Stub.so` | Host-side stub. `libQnnHtp.so` loads the matching one by name. |
| `libQnnHtpV<N>Skel.so` | DSP-side skeleton. Loaded onto Hexagon through `ADSP_LIBRARY_PATH`. |
| `libQnnHtpPrepare.so` | Graph preparation library. **Required**: without it the HTP backend fails with `HTP Prepare backend loading failed` and no graph can be created. |
| `libQnnCpu.so` | QNN CPU backend; not used (burn-npu has its own CPU fallback). |

The Hexagon generation names are approximate; confirm against Qualcomm's
current HTP documentation for your SoC:

| Hexagon | Typical Snapdragon class |
| --- | --- |
| V68 | Snapdragon 888 / 888+ |
| V69 | Snapdragon 8 Gen 1 / 8+ Gen 1 |
| V73 | Snapdragon 8 Gen 2 and many 7-series parts |
| V75 | Snapdragon 8 Gen 3 / 8s Gen 3 |
| V79 | Snapdragon 8 Elite class |
| V81 | Newer 2025+ flagships |

Including every generation makes the APK large (this repository's debug APK is
about **88 MB** with V68–V81). Trim the list to the devices you care about:

```sh
QNN_HEXAGON_VERSIONS="79" just qnn-libs
```

### 5.2 Copy the libraries

```sh
QNN_SDK_ROOT="$HOME/.cache/burn-phone/qairt/2.52.0.261104" just qnn-libs
just qnn-status
```

Result:

```text
qnn-libs/
├── arm64-v8a/
│   ├── libQnnHtp.so
│   ├── libQnnHtpPrepare.so
│   ├── libQnnSystem.so
│   ├── libQnnHtpV79Stub.so
│   └── libQnnHtpV79Skel.so
│   └── ...
└── x86_64/            # intentionally empty
```

`cargo-apk` requires a directory for **every** ABI in `build_targets`. The
x86_64 directory is therefore present but empty, so the emulator build works
and simply runs on CPU.

The `.so` files are ignored by git:

```gitignore
/qnn-libs/*/*.so
```

They are Qualcomm proprietary binaries and should not be committed.

### 5.3 Manifest configuration

```toml
[package.metadata.android]
runtime_libs = "qnn-libs"

[package.metadata.android.sdk]
min_sdk_version = 28
target_sdk_version = 30

[package.metadata.android.application]
extract_native_libs = true
```

`extract_native_libs = true` is required: the Hexagon DSP loader reads the
skel files from a real filesystem path, not from inside the APK.

`target_sdk_version = 30` is required on current Android. The QNN stub links
against the vendor library `libcdsprpc.so` (FastRPC). Android 12+ hides vendor
libraries from apps targeting API 31 or newer unless the app declares them with
`<uses-native-library android:name="libcdsprpc.so"/>`. cargo-apk 0.10 cannot
emit that element, so the app targets API 30 to keep the legacy linker
namespace. On the phone, the linker otherwise reports:

```text
library "libcdsprpc.so" ... is not accessible for the namespace: [name="clns-9" ...]
```

The NPU path needs both `libcdsprpc.so` and the app-side preload in section 6.
If you later move to a newer target SDK, add the `uses-native-library` entry to
the generated manifest first.

`cargo-apk` copies the libraries into `lib/arm64-v8a/`, and `zipalign` runs
afterwards. The APK can be inspected with:

```sh
unzip -l target/debug/apk/burn-phone.apk | grep -E 'libQnn|libburn'
```

## 6. Runtime setup on Android

`libQnnHtp.so` needs to know where the skels live. Set
`ADSP_LIBRARY_PATH` before the first matmul. Android extracts native libraries
into an app-private directory whose path is not directly exposed to Rust, so
derive it from `/proc/self/maps`:

```rust
#[cfg(target_os = "android")]
fn configure_adsp_library_path() {
    let Some(dir) = native_lib_dir() else {
        log::warn!("could not locate the app's native library directory");
        return;
    };
    log::info!("ADSP_LIBRARY_PATH={}", dir.display());
    // Called from android_main before any other thread starts.
    unsafe { std::env::set_var("ADSP_LIBRARY_PATH", &dir); }
    preload_cdsprpc();
}

/// Load the vendor FastRPC library by absolute path with RTLD_GLOBAL so the
/// HTP stub's `libcdsprpc.so` dependency resolves to the already-loaded copy.
#[cfg(target_os = "android")]
fn preload_cdsprpc() {
    for path in ["/vendor/lib64/libcdsprpc.so", "/system/lib64/libcdsprpc.so"] {
        if !std::path::Path::new(path).exists() {
            continue;
        }
        let result = unsafe {
            libloading::os::unix::Library::open(
                Some(path),
                libloading::os::unix::RTLD_NOW | libloading::os::unix::RTLD_GLOBAL,
            )
        };
        match result {
            Ok(lib) => {
                log::info!("preloaded {path}");
                std::mem::forget(lib);
                return;
            }
            Err(err) => log::warn!("could not preload {path}: {err}"),
        }
    }
}

#[cfg(target_os = "android")]
fn native_lib_dir() -> Option<std::path::PathBuf> {
    let maps = std::fs::read_to_string("/proc/self/maps").ok()?;
    for line in maps.lines() {
        for field in line.split_whitespace() {
            if field.ends_with("/libburn_phone.so") {
                return std::path::Path::new(field).parent().map(Path::to_path_buf);
            }
        }
    }
    None
}
```

Call it as the first thing in `android_main`:

```rust
#[cfg(target_os = "android")]
#[unsafe(no_mangle)]
pub fn android_main(app: winit::platform::android::activity::AndroidApp) {
    android_logger::init_once(
        android_logger::Config::default()
            .with_max_level(log::LevelFilter::Info)
            .with_tag("burn-phone"),
    );

    configure_adsp_library_path();

    let mut options = native_options();
    options.android_app = Some(app);
    // ...
}
```

On a phone, the resulting directory is similar to:

```text
/data/app/~~<random>/dev.burnphone.app-<random>/lib/arm64/
```

and the skels are files such as `libQnnHtpV79Skel.so` inside it.

Do not hard-code `/data/app/...`; it changes on every install.

## 7. Using the backend

```rust
use burn::tensor::Tensor;
use burn_npu::{NpuBurnBackend, NpuBurnDevice};

type B = NpuBurnBackend;

let device = NpuBurnDevice::Default;

let x = Tensor::<B, 4>::full([1, 3, 224, 224], 0.5, &device);
let model = generated::Model::<B>::from_embedded(&device);

// First call also creates the QNN context and finalizes a graph for each op
// shape it sees. Later calls for the same shape reuse the cached graph.
let logits = model.forward(x);
```

`generated::Model` is the SqueezeNet model generated by `build.rs` from the ONNX
file (see `src/classifier.rs`).

### 7.1 Ops that run on the Hexagon

The SqueezeNet classifier (`src/classifier.rs`) runs its forward pass through
`NpuBurnBackend`. Each op asks the QNN path first and falls back to the CPU
when the QNN path declines. The NPU-enabled ops are:

| Op | Entry point | Minimum size (elements) |
| --- | --- | --- |
| Conv2d | `try_conv2d` | output ≥ 4096 |
| Max/avg pool | `try_pool2d` | output ≥ 4096 |
| ReLU | `try_relu` | input ≥ 4096 |
| Concat | `try_concat` | output ≥ 4096 |
| Softmax (last axis) | `try_softmax` | input ≥ 1024 |

Small tensors stay on the CPU because graph creation and transfers would
dominate. Ops are compiled only with the `qualcomm` feature (not `intel`) and
only when the SDK is present (`qnn_sdk` cfg).

Each op's graph is built once per shape and then cached. On the first run,
building costs about 8–45 ms per new shape. Conv weights are converted from
OIHW to HWIO once per weight buffer and cached. The classifier keeps its model
loaded so those buffers stay at fixed addresses.

### 7.2 Dispatch threshold and fallback

Every failure path — SDK not compiled in, `libQnnHtp.so` missing, no Hexagon
device, unsupported shape, graph finalize error — falls back silently to the
CPU op.

To make this visible, the vendored backend exposes:

```rust
burn_npu::backends::qualcomm::qnn_compiled();
burn_npu::backends::qualcomm::npu_dispatch_count();
burn_npu::backends::qualcomm::set_force_cpu(true); // CPU-only, for benchmarks
```

`npu_dispatch_count()` is process-wide. The classifier records the count
before and after one classification and reports the difference as
"Executed on: Hexagon NPU (N ops)":

```rust
let before = burn_npu::backends::qualcomm::npu_dispatch_count();
let values = forward(&input);
let ops = burn_npu::backends::qualcomm::npu_dispatch_count() - before;
```

- `ops > 0` → those ops ran on Hexagon.
- `ops == 0` → CPU only (or every op was below its threshold).

### 7.3 Per-op timing

Set `BURN_NPU_TIMING=1` in the environment, or on Android set the system
property `debug.burnnpu.timing` to `1`. Each op then logs a line with its build
and execution time:

```sh
adb shell setprop debug.burnnpu.timing 1
adb logcat -d | grep npu-op
adb shell setprop debug.burnnpu.timing 0
```

The environment variable does not reach a `NativeActivity` process, so use the
property on the phone.

### 7.4 CPU vs NPU benchmark

The app's benchmark button runs `classifier::benchmark` on `tests/data/cat.jpg`.
It does one warm-up run per path, then times the CPU and NPU paths. Each timed
run covers the whole `classify` call: preprocessing (resize and normalize), the
forward pass, and the softmax. Results on the Nothing Phone (SM8475), with 34
NPU ops:

Dev build (`just build`, the unoptimized app crate):

| Run | CPU | NPU | NPU / CPU speed |
| --- | --- | --- | --- |
| 1 | 245.2 ms | 515.4 ms | 0.48× |
| 2 | 313.6 ms | 516.4 ms | 0.61× |
| 3 | 301.6 ms | 463.1 ms | 0.65× |
| Mean | 286.8 ms | 498.3 ms | 0.58× |

Release build (`just build-release`):

| Run | CPU | NPU | NPU / CPU speed |
| --- | --- | --- | --- |
| 1 | 50.9 ms | 82.1 ms | 0.62× |
| 2 | 51.8 ms | 112.4 ms | 0.46× |

All runs return the same top four classes (Egyptian cat 59.0%, lynx 12.6%,
red fox 10.0%, grey fox 6.0%). The release numbers vary by about 30 ms on the
NPU path, so two runs are not enough to rank the two builds finely.

The release build is 5–6× faster on both paths, which shows that the dev build
was dominated by unoptimized app-crate code. Preprocessing on the dev build
took about 144 ms per call, and the release build is faster on that as well.

Where the NPU time goes (release, timed pass, 34 ops):

- The QNN `graphExecute` calls add up to about 20–22 ms.
- The op timestamps span about 91 ms, so about 69 ms is host work between ops,
  about 2 ms per op.
- Layout conversion is not the cause. In a release host build, NCHW→NHWC for the
  largest conv input (64×55×55) takes about 0.29 ms and NHWC→NCHW about 0.08 ms.
  Across SqueezeNet's convs and pools that is well under 10 ms per call.
- Per-op `run_op` costs (key formatting, dims clones, output allocation) were
  measured as small: the key takes about 0.1 ms and the output allocation
  about 0.5 ms across the 34 ops.

The remaining host time is not yet attributed. An attempt to split it per stage
(key, lookup, allocation, execute, layout) did not log any conv or pool ops, so
the breakdown is incomplete and those timers were removed. The NPU path is
currently slower than the CPU for this model.

### 7.5 Fused graph (default, faster than the CPU)

`src/squeezenet_fused.rs` and `build_fused` in `qnn.rs` build the whole
SqueezeNet network as one QNN graph, which removes the per-op host round trips.
It is the default NPU path. Build it with `just build-fused` (or `just build`,
which uses the same `support-hexagon` branch of `burn-npu`). Set the
`debug.burnnpu.fused` system property to `0` to force the slower per-op path.

Two graph-construction bugs used to block this path on the SM8475 HTP. Both are
now fixed:

- **Duplicate graph and node names** (`Graph name is a duplicate`) — graphs were
  named by op/shape only, so a retry after a failed build reused a name the DSP
  had already registered, and every fused `Conv2d` node had the same name. Graph
  and node names now include a global atomic build id.
- **Tensor params not registered** (`Failed to create InputDef ... param
  stride` / `filter_size`) — `stride`, `pad_amount`, `dilation` and
  `filter_size` are `UINT_32` tensor params. They must be created as static
  `FLAT_BUFFER` tensors with `QNN_DEFINITION_UNDEFINED` /
  `QNN_QUANTIZATION_ENCODING_UNDEFINED`, registered with
  `tensorCreateGraphTensor` *before* `graphAddNode`, and kept alive until
  `graphFinalize`.

See [QNN graph-build pitfalls](qnn-graph-build-pitfalls.md) for the symptoms,
root causes and the exact setup.

Measured on the SM8475 (Nothing Phone, Hexagon V69) with `just benchmark`:

| Path | Build | Compute | Total | Result |
| --- | --- | --- | --- | --- |
| CPU | — | — | ~144–154 ms | Egyptian cat 63.4% |
| Fused NPU | one-time, ~0.2–10 s | ~1 ms | ~2.6–4.8 ms | Egyptian cat 63.3% |

The fused NPU path is roughly **30–60× faster** than the CPU and selects the same
top classes. The graph build is one-time per process and is not included in the
timed total; how long it takes varies with the DSP/HTP prepare state.

Two changes made this possible:

- Preprocessing (RGBA → 224×224 area-average → normalized NCHW) now writes
  directly from the RGBA bytes into the NCHW buffer instead of allocating two
  intermediate images through `image::imageops::resize`. It takes ~1.5–2 ms.
- The app crate is built with `opt-level = 2` in the dev profile, so its
  preprocessing and layout-conversion loops are not left unoptimized. The NPU
  executes the fused model in ~1 ms.

The device still logs an SELinux `avc: denied` for
`adsprpcd_file`/`vendor_xdsp_device` during device creation. The NPU ops still
run.

### 7.2 Runtime probe

The UI also probes whether the HTP backend can be opened:

```rust
fn probe_qnn_runtime() -> Result<String, String> {
    match unsafe { libloading::Library::new("libQnnHtp.so") } {
        Ok(_) => Ok("libQnnHtp.so loaded".to_string()),
        Err(err) => Err(err.to_string()),
    }
}
```

This is only a load test; it does not create a backend or execute a graph.
The real initialization happens lazily on the first NPU op.


For comparison, the same run on the CPU fallback took about 1146 ms warm. The
checksum differs slightly from the CPU result (26772.664) because the HTP
computes in reduced precision.

On the x86_64 emulator:

```text
QNN SDK:      compiled in (...)
Device:       No Qualcomm NPU detected (android/x86_64)
HTP runtime:  not loadable -- libQnnHtp.so: cannot open shared object file
Result:       Executed on: CPU fallback
```

That is expected: no x86_64 QNN libraries are bundled.

## 9. Verifying the DSP/Hexagon generation

Useful device properties:

```sh
adb shell getprop ro.soc.model
adb shell getprop ro.board.platform
adb shell getprop ro.hardware
adb shell getprop ro.product.cpu.abi
adb shell ls /sys/devices/soc0/
```

`ro.soc.model` / `ro.board.platform` identify the SoC; map it to the Hexagon
generation with Qualcomm's HTP documentation (or try the matching
`libQnnHtpV<N>Stub.so`). The app reports the detected model in its status
section.

If the HTP library loads but `npu_dispatch_count()` stays at zero:

1. Confirm the APK contains `libQnnHtpV<N>Stub.so` and `libQnnHtpV<N>Skel.so`.
2. Confirm `ADSP_LIBRARY_PATH` appears in logcat and points at the extracted
   native library directory.
3. Confirm the skels were actually extracted (`extractNativeLibs = true`).
4. Confirm the op is large enough for its threshold (section 7.1).
5. Check logcat for graph-finalize or DSP errors.

## 10. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `warning: QNN_SDK_ROOT not set` | Export `QNN_SDK_ROOT` before building, then rebuild `burn-npu`. |
| `bindgen failed on the QNN headers` | Missing `libclang` or wrong `QNN_SDK_ROOT`; install `clang`/`libclang-dev`, or set `LIBCLANG_PATH`. |
| Compile error mentioning `v2_31` or `QNN_INTERFACE_VER_TYPE` | You are building upstream burn-npu against a newer/older SDK. Use the vendored patch or apply the same changes. |
| `HTP runtime: not loadable` on a phone | `libQnnHtp.so` is missing from the APK, the ABI is wrong, or minSdk is too low. Check `unzip -l` and `adb shell getprop ro.product.cpu.abi`. |
| HTP loads but every result says CPU fallback | Graph creation failed; look for `QnnUnavailable`/DSP errors in logcat, verify skel + `ADSP_LIBRARY_PATH`, and try a larger tensor. |
| DSP error about skel not found | The skels were not extracted, or `ADSP_LIBRARY_PATH` points at the APK instead of the extracted lib directory. |
| `INSTALL_FAILED_INSUFFICIENT_STORAGE` | The debug APK is ~88 MB with all Hexagon generations. Build with `QNN_HEXAGON_VERSIONS="79"` or use a release build. |
| Emulator reports CPU fallback | Expected: the emulator is x86_64 and no x86_64 QNN runtime is bundled. Test on a Snapdragon phone. |
| App crashes immediately after adding QNN libs | Check `adb logcat` for `dlopen` failures; usually an ABI mismatch or a missing dependency of `libQnnHtp.so` (`libc.so`, `libm.so`, `libdl.so`, `liblog.so`, `libcdsprpc.so` are supplied by Android). |
| `bindgen failed on the QNN headers: ... 'gnu/stubs-32.h' file not found` | Android build is using host glibc headers. Set `ANDROID_NDK_HOME` and rebuild with the vendored `build.rs` (section 4.1). |
| `QNN SDK: bindgen did not run` on the phone | The Android build did not get `cfg(qnn_sdk)`; see section 4.1 and check the `burn-npu` build output. |
| `library "libcdsprpc.so" ... is not accessible for the namespace` | The app targets API 31+. Set `target_sdk_version = 30` (section 5.3), and make sure the preload in section 6 runs. |
| `HTP Prepare backend loading failed` / `libQnnHtpPrepare.so not found` | Add `libQnnHtpPrepare.so` to `qnn-libs/arm64-v8a` (`just qnn-libs` copies it) and rebuild the APK. |
| Segfault inside `libQnnHtp.so` when pressing Run benchmark | Tensor or op config `version` tag is not set; the vendored `qnn.rs` sets it (section 2.1). |
| `Use of QNN_DEFINITION_IMPL_GENERATED tensor not supported as input for MatMul` | Quantization params left zeroed; the vendored `qnn.rs` sets them to defined/undefined encoding (section 2.1). |
| `Failed to create InputDef for Op Conv2d_0 ... param stride` (or `filter_size`) | Tensor params must be registered with `tensorCreateGraphTensor` before `graphAddNode` and use undefined quantization; see [QNN graph-build pitfalls](qnn-graph-build-pitfalls.md). |
| `Graph name is a duplicate` | Graph/node names must be unique for the context lifetime, including failed-and-retried builds; the vendored `qnn.rs` appends a global build id. See [QNN graph-build pitfalls](qnn-graph-build-pitfalls.md). |
| `Expected Tensor ID: N not found in user-provided tensors` | Tensor IDs from graph construction were not reused at execute time; the vendored `qnn.rs` caches them per graph (section 2.1). |
| 16 KB page-size device refuses a library | Check `llvm-readelf -l libQnnHtp.so \| grep LOAD` alignment; use a QNN SDK build that is 16 KB-aligned. |

Rebuild from a clean state when changing SDK paths or versions:

```sh
cargo clean -p burn-npu -p burn-phone
QNN_SDK_ROOT="$HOME/.cache/burn-phone/qairt/2.52.0.261104" just build-fused
```
